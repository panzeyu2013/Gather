## 0. 总体结论

- **未发现 P0**（崩溃/数据丢失/编译中断/安全）：168 文件全部 parse 通过；风险最高的两个"可能编译失败"写法（`Synchronization.Mutex` 存 `NSRegularExpression`、`@Observable` + `didSet` + `@ObservationIgnored`）用 Swift 6.2 严格并发在 Linux 上独立编译并运行通过；`PRAGMA optimize` 新建 `sqlite_stat1` **不会**触发 schema 形状/表数断言（全仓 4 处 schema 读取均过滤 `name NOT LIKE 'sqlite_%'`，已逐一核对）。
- **1 个 P1**：`navigationGroupSizeByPhotoID` 的缓存命中路径不读取任何被 Observation 跟踪的属性 → 缓存命中后丢失对 `navigationGroups` 的依赖，导航组变化可能不刷新"组 N 张"徽标。已用 `withObservationTracking` 探针 A/B 复现（A 不触发 / B 触发）。
- **主要 P2**：JSON "逐字节一致"论断在 swift-foundation 上不成立（同值两个 encoder 输出可不同，实测 fresh-vs-fresh 200/200 不同）→ 证据被夸大、新增测试断言的是 Foundation 不保证的性质；`NavigationService.LegacyWallDateParsers` 无锁共享 `DateFormatter`（与本仓自己"DateFormatter 非线程安全"的既有约定矛盾）；`Task.sleep` 取消语义把 200ms 退避变成 0（停机路径行为变化）；NSCache cost 修正后 512MB 上限对高 DPI 图从"形同虚设"变成"真正生效"，淘汰悬崖未评估。
- **最优性判断**：DBStatementCache（按作用域+limit 的保守设计）、mmap、page-index/布局/选择集缓存、LRU/throttle 均属**合理且低复杂度**；轻微过度设计是"每个调用点手工注释/手工 limit"，以及 perf ratchet 的 9 个 JSON/日期构造点指标需要"改基线记账"的长期维护成本。**不建议回退任何一项**，建议修 P1 + 补测试 + 降级两处论断。

### 1.1 已核对但**不构成**问题的"疑似"项（避免 lead 重复排查）

- **`PRAGMA optimize` 会不会破坏 schema 断言**：不会。四类 schema 读取全部过滤 `sqlite_%`（`SchemaShape.swift:92-96` 表名查询、`BackupVerifier.swift:99-106` 表数、`OpenState.swift:120-128` userTableCount、`DiagnosticsQuery`）；`user_version` 不变（python 探针实测）；`sqlite_stat1` 的创建只会让 `PRAGMA schema_version` 变化，仓内无 consumer。
- **`PRAGMA optimize` 在事务中**：python 探针实测不抛错（no-op）。
- **`PRAGMA optimize` 把 close 拖到 5s**：不会；`busy_timeout=250` 实测外部写锁下 251ms 快速失败，`BestEffort` 吞掉。
- **mmap 与 WAL/只读池/`:memory:`**：逐连接生效、只读+`query_only` 连接可设、`:memory:` 查询返回 NULL（因此 `path != ":memory:"` 的跳过是正确的，非多余）。
- **`@Observable` + `didSet` + `@ObservationIgnored` 是否编译/是否破坏观察**：编译通过（Swift 6.2 strict concurrency + warnings-as-errors），且用 `withObservationTracking` 可观察到 didSet 的失效（`obs3.swift`）——round-3 文档的同类结论可复现。
- **`Synchronization.Mutex` 存 `NSRegularExpression`（非 Sendable）**：在 Swift 6.2 下编译并通过 strict concurrency（`mutex_probe.swift`）；不会成为 P0 编译中断。
- **`DBStatementCache` 的 9 个调用点**：只读站均 limit=1（末块现场 prepare），limit>1 站点（14/5/2）全部在 `connection.transaction` 闭包内 ⇒ 语句建在写连接、不占只读池；缓存不跨事务边界（`AssetRepo+Scan` 每批事务内新建）。**没有发现越界使用**。
