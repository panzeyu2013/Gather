## 0. 结论先行

1. **模型级初审不需要自研/下载模型**。Vision 已提供人脸关键点（眼睛/嘴唇）、`faceCaptureQuality`、
   注意力显著性、审美分（macOS 15+）；CIDetector 提供眨眼/微笑布尔值。本机实测单张 60–120 ms，
   20k 张在 6 并发下约 5–8 分钟，可作为后台 job。
2. **现有 triage 的「闭眼」不是模型，是代理指标**：`QualityService.swift:280-295` 在 512px 缩略图的
   最大人脸上取「眼部框梯度 / 人脸框梯度」；合影里人脸只占画面几个百分点时，眼部框只有十几像素，
   这个比值的方差远大于信号。改模型信号是**替换传感器**，不是调参。
3. **JPEG 内嵌写必须做段级（APP1/APP13）改写，不能只靠 ImageIO 的 metadata 复制**。实测：
   `CGImageDestinationCopyImageSource` 能保住像素（解码哈希一致）也能写 XMP，但**忽略 IPTC 字典**
   （写后 IIM 仍是旧值）。而「清空」的语义要求 IIM 数据集被删除，所以段级改写是唯一可靠路径。
4. **清空失效的根因在读侧，不在写侧**：`MetadataService.descriptiveFromParse` 的 `firstText` 按
   dc → xmp → IIM 逐级回退且**跳过空值**（`MetadataService.swift:461-469`），所以只清 XMP 时旧 IIM 会
   「复活」；同时写后回读只看 sidecar（`MetadataService.swift:1099`），再把 sidecar 快照写回投影
   （`1138-1141`），会把仅存在于内嵌的其它字段一起从面板抹掉。
5. **交付闭环的缺口是「产品层」而非「引擎层」**：`ExportService` 已有预览/续跑/回滚/指纹/报表，
   但 `ExportOptions`（`Export.swift:81-116`）只有一套参数，没有配方、联系表、打印、画廊、发布。
6. 三条需求合起来约 **36–40 PD**；2 人并行约 5 周（含门禁与人工矩阵）。

## 2. 设计

### 2.1 模型级初审（T1）

#### 2.1.1 信号层：只用系统模型，产出可解释的连续分

新增 `ModelReviewService`（GatherApplication/Services/ModelReview/），逐张产出：

| 信号 | 算法 | 成本（实测） | 备注 |
|---|---|---|---|
| `primaryFace` | 已有 `face_observations`（bbox 归一化、quality、roll）；按 `area × captureQuality` 排序，居中加权 | 0（DB） | 不再用「最大脸 = 主体」 |
| `eyeOpen`（每脸） | `VNDetectFaceLandmarksRequest` 取 `leftEye/rightEye` 6 点 → EAR = (‖p2−p6‖+‖p3−p5‖)/(2‖p1−p4‖)；按脸宽分箱校准 → 0…1 | 24–31 ms | 眼区 ROI 传 `regionOfInterest`，实测 28 ms |
| `eyeBlink`（交叉验证） | `CIDetector(eyeBlink: true)`；仅在 EAR ∈ [0.15, 0.25] 的歧义区调用 | 108 ms/张（高精度） | 只在歧义时用，避免全量成本 |
| `smile`（每脸） | outerLips/innerLips 关键点 → 嘴角上扬度 + 嘴宽/脸宽比 → 0…1；歧义时用 `CIDetector(smile: true)` | 0（复用关键点） | 表情只做「加分项」，永不单独 reject |
| `faceFocus` | `RAWDecoder.decodeRegion`（已有，`RAWDecoder.swift:130-185`）按人脸框取 ≥ 384px 裁片 → Tenengrad/拉普拉斯方差 ÷ 局部对比度归一 | 30–60 ms | 解决「512 图上小脸只有十几像素」 |
| `subjectFocus` | `VNGenerateAttentionBasedSaliencyImageRequest` → 显著框 → 同法在 1024 图上测锐度 | 20–30 ms | 无脸照片（商品/风光）也有主体判据 |
| `aesthetic` / `isUtility` | `VNCalculateImageAestheticsScoresRequest`（macOS 15+） | 12–17 ms | macOS 14 走降级：无审美分，`warnings += aesthetic_unavailable` |
| `captureQuality` | `VNDetectFaceCaptureQualityRequest`（可传已有 observation） | 26–31 ms | 光照/姿态/表情的综合质量，作 keep 侧证据 |

> 实测环境：macOS 27.0.1 / SDK 27，1400×885 截图；冷启动首帧 400 ms（模型加载），此后为稳态值。
> 不引入任何第三方模型；`VNCalculateImageAestheticsScoresRequest` 需要 `if #available(macOS 15, *)`，
> 部署目标仍是 14.0。

### 2.2 JPEG 内嵌 IPTC 写/清（B3）

#### 2.2.1 目标模型：一个「物理写目标」，不是两个真相源

引入 `MetadataTarget`（Protocol 层纯值）：

规则（`MetadataTargetPolicy`，可单测的纯函数）：

| 照片 | `metadata_write_mode` | 目标 |
|---|---|---|
| RAW / 非 JPEG（HEIC、TIFF…） | 任意 | sidecar（v1 只做 JPEG 内嵌） |
| JPEG 且同资产有 RAW 兄弟 | 任意 | sidecar（一份真相，C1/Bridge 惯例） |
| 独立 JPEG | `sidecar` | sidecar（旧行为） |
| 独立 JPEG | `auto` / `embedded` | embedded |

#### 2.2.2 段级写入器（宿主，`gather-app/Sources/GatherHost/Embedded/`）

    JPEGSegmentTable     解析 SOI…SOS：段列表(offset/len/payload)、scanRange；校验截断
    XMPPacketStore       定位 APP1 "http://ns.adobe.com/xap/1.0/"；解码/编码；复用 SidecarXMPProvider.patchDocument
    IPTCIIMStore         定位 APP13 "Photoshop 3.0" → IRB 0x0404；按 dataset 读写（1:90 UTF-8 标志）
    JPEGMetadataWriter   替换/删除 APP1-XMP、APP13-IRB → 重建头部 + 原样拼接 SOS…EOI
    HeaderBackup         保存 SOI…SOS 前缀（几 KB–几百 KB）+ manifest；restore = 旧头部 + 当前 scan

硬约束（每条都有测试）：
1. **scan 字节不变**：写前后 `SHA256(scanRange)` 必等；写后仍可被 ImageIO 解码且像素哈希一致。
2. 未触及的段逐字节保留（`APP0/APP1-Exif/APP2/APP14/COM` 全部入账，做段级 diff 断言）。
3. 原子写：同目录临时文件 → `fsync` → `replaceItemAt`；保留权限/扩展属性。
4. 写后校验：ImageIO 重读 + 自有解析器双读，逐字段比对；失败即 `EMBEDDED_WRITE_VERIFICATION_FAILED`。
5. 上限：XMP packet ≤ 64 KB（APP1 长度上限 65533）；超限显式失败，不静默截断。
6. 拒绝：损坏/截断/非 JPEG/只读卷 → 类型化错误码，不写半成品。

#### 2.2.4 路由与交付层接线（只在两处开缝）

交付队列（`GatherDelivery`，804 处 `xmpPath` 引用）**不重写**，只做两处参数化：

1. **目标解析**：`DeliveryTypes.swift:36`、`WritebackService+Helpers.swift:165/279`、`+Execute.swift:369`
   统一走 `MetadataTargetPolicy.resolve(photo:)`；`deliveries.xmp_path` 落 `target.writePath`
   （embedded 时等于照片路径），并新增 `target_kind` 列（v6）作为**语义真相**，不再靠「路径像不像 sidecar」猜。
2. **写/验/恢复**：`XMPProvider` 之上加 `MetadataWriteRouter`（装饰器）：
   - `writeAttributes` → sidecar 走原实现；embedded 走 `JPEGMetadataWriter`；
   - `backup/restore` → embedded 走 `HeaderBackup`（只备份头部，不复制整张 5 MB JPEG）；
   - `readAttributes` → 返回**有效属性**（内嵌 + sidecar 合并），写后校验因此不再自欺。

安全守卫扩展：`DeliveryXMPPath.requireSafeSidecar`（`DeliveryBackupPath.swift:152-169`）当前只校验
「绝对路径 + 无 .. + 同目录」，embedded 时 `xmpPath == photoPath` 能通过；但必须新增
`requireSafeTarget(kind:)` 显式要求「embedded 时目标必须等于解析后的照片路径」，防止 DB 被篡改后
让 cleanup 去删任意 JPEG。备份路径继续走 `DeliveryBackupPath.validate`。

#### 2.2.5 清空语义（三态）与回读统一

- 三态沿用 `DescriptiveMetadata`：`nil` 不动 / 空串清空 / 有值写入。
- **清空 = 两处都删**：XMP 删元素且 **IIM 删 dataset**；只存在于 XMP 的字段（contact、
  `Iptc4xmpExt` 等）只删 XMP。
- **读侧防复活**：`MetadataParseSegments` 增加 `xmpPresentKeys: Set<String>`（ImageIO 枚举标签时顺带记录），
  `firstText/firstList` 命中「存在但为空」时**停止回退**。这样即使外部又写了空 XMP，也不会被旧 IIM 盖回来。
- 回读/投影：`applyMetadataAttributes` 的 `actual` 改 `diskAttributes(photoPath:)`（`:1099`），
  投影用有效值（`:1138-1141`）。修掉「清一个字段，其它内嵌字段从面板消失」。
- sidecar 共存：embedded 模式下若盘上已有 Gather 管理的 `.xmp`，首次写入前执行
  **sidecar→embedded 合并 + sidecar 归档**（改名 `.xmp.gather-archived-<ts>`，在报表里列出），
  避免两个真相源（见 §6 未决 3）。

#### 2.2.6 备份 / 撤销 / 冲突

- `deliveries.backup_path` 语义不变，但 embedded 时指向 **header backup**（`.jpg.gather-header-<uuid>`）。
- 冲突检测：`base_fingerprint` 改为「头部段指纹 + 文件 size/mtime」；外部改了 XMP 段即判 conflict，
  转人工裁决，绝不静默覆盖。
- 撤销（模板/triage 批次）继续走 `MetadataApplyBatchStore` 快照 + 交付 cleanup；embedded 时
  cleanup 用 header backup 还原头部（scan 不动），并复核像素哈希。

#### 2.2.7 迁移与灰度

1. 设置开关落地（`metadata_write_mode` 真正生效，默认仍是 `sidecar`，灰度：`auto` 只在新建会话生效）。
2. 一次性迁移任务（可选、可回滚）：对「独立 JPEG + 我们有 sidecar」的照片执行合并入内嵌 + 归档 sidecar，
   产出 CSV 报表（成功/跳过/失败）。**默认不自动跑**，由设置页显式触发。
3. 回滚：归档文件保留 30 天；`maintenance cleanup` 不删它们（显式白名单）。

### 8.1 设计反思（自我批判，10 条）

| # | 原设计的问题 | 修订 |

| R4 | `keepScore` 手写权重 = 把主观判断包装成数字，且没有拟合数据 | 保留 v1 排序键 `qualityScore`，只加两个**有序** tie-break（captureQuality、smile）；文档明写「不做加权复合分」 |
| R5 | 独立 `model.review` job = 注册/取消/重试/UI 映射又一整套 | **并入 `quality.score` 执行体**（同 worker、同一次解码），结果写另一个 `analysis_type`；checkpoint 加 `stages` |
| R6 | 「清空」责任分散在写侧与读侧，容易只修一半 | 三条缺一不可：**IIM 删 dataset（前提）→ XMP 删元素（补充）→ 读侧 presence 阻断回退（兜底）** |
| R7 | sidecar→内嵌迁移是我给自己造的活，且引入新的失败模式 | **规则即策略**：盘上存在同名 `.xmp` → 目标永远是 sidecar；只有「无 sidecar 的独立 JPEG」才内嵌。删除迁移任务 |
| R8 | `deliveries.xmp_path` 改名 804 处，收益只有命名一致 | 不改名；新增 `target_kind`，新代码用 `MetadataTarget`，DDL 注释写明「xmp_path = 写目标路径」 |
| R9 | 打印做成 host 服务只会多一层协议面 | 打印 = 导出页/文件菜单的一个函数，输入是已有 PDF |
| R10 | 联系表与画廊的失败模式不同，合成一波验收含糊 | 拆 W3a（配方+编排+联系表+打印+转码保真）/ W3b（画廊+校样+发布） |
| R11 | 「自动应用」被当成收益点 | 收益来自「review 变少」+「一键接受整组」；自动应用复用既有 `applyTriage(minConfidence)`，不新增调度器 |

### 8.2 简洁性反思（净删除项）

| 原设计 | 修订 | 省 |
|---|---|---|
| 新 job 类型 `model.review` | 并入 `quality.score` | 1 个 executor + 注册/取消/UI 映射（≈1.5 PD） |
