### 0.2 三条最重要的判断

1. **第 1 条不是"记账问题"，是生命周期缺口。** 每条交付行是"每个 xmp_path 一行"（`deliveries.xmp_path UNIQUE`，DDL:220），不是每次写盘一行；真正的增长是"每个被写过的文件一行 + 一份备份永远不回收"，再加每个文件 × 每个模块一条 item（`UNIQUE(delivery_id, photo_id, module)`）。metadata 模块**没有任何确认/结束入口**，所以：
   - 行现在一直停在 `written`（没有确认/结束入口），备份永远保留；
   - 共享文件上，跨模块清理门禁会看到 `.incomplete(metadata, written)`（`DeliveryDBPhase.swift:197-211`）而整条跳过；
   - 客户校样导入（`LiveCullingAPI.swift:303`）也会入队 metadata 写回，把同一个漏洞扩大到"每导入一次校样就多一批永不清理的行"；
   - 更糟的是 `requireReloadAck` 在组合根取默认 `true`（`DeliveryCoordinator.swift:250`，`Core.swift:124` 未覆盖）：**没用 C1 的用户连 culling confirm 都过不去**，cleanup/finalize 全部死路。W1 要把这个门禁改成按 C1 配置动态启用。

   本波必须先把"确认 → 结束/清理 → 备份回收"补齐，再做后面的能力；否则新功能（校样反馈、关键词、集合）只会加速这张表膨胀。

2. **第 2 条的性能问题在端口层，不在某个函数。** 现在 `XMPProvider` 的四个方法各自把整文件读一遍：指纹、备份、读属性、写盘、写后校验、写后回读，各读一次（§1.2）。单点优化（比如只改 `JPEGDocument`）省不掉重复读；必须引入"一次打开、一次读、多处用"的会话端口，并让写盘与校验共享同一份字节流。

3. **schema 继续 v1，直接扩展 DDL。** 关键词库、集合/堆栈、校样反馈、语义索引都需要持久化；开发期不 bump 版本、不写迁移，新表直接进当前 DDL，旧开发库按既有 `ResetPolicy` 归档重建。代价是"开发机旧库会丢"，收益是只有一份建库真相、没有迁移链。

## 1. 现状核对（代码证据）

### 1.1 交付与备份：一张表、两条泄漏路径

```
排队（MetadataMutationService.queuePhotoValues）          执行（WritebackService.execute）
  deliveries  ⋯ 1 行 / xmp_path（UNIQUE，DDL:220）   →   status: pending → writing → written
  delivery_items ⋯ 1 行 / (delivery, photo, module)  →   item: pending → written
  backup_path ← xmp.backup()（首次写前）                  →   .gather-header-* / .gather-backup-* 落盘
                                                          
确认（只有 culling/face/similarity 有）                   结束（只有 culling/face/similarity 有）
  DeliveryRepo.confirm → written→synced（跨模块写 items）  Coordinator.finalize → 删行 + 删备份
```

- metadata/template 模块**没有**第 2 段调用点：`MetadataAPI` 全协议（`MetadataAPI.swift:18-66`）没有 confirm/cleanup/finalize；`MetadataMutationService` 以 `module: .metadata` 开行（`MetadataMutationService.swift:274`），`MetadataService` 的关键词预览也是同一模块（`MetadataService.swift:985`），但入队之后没有任何收尾入口。
- 结果 A（行/备份泄漏）：文件被写过一次 → 行 + item + 备份永久存在。再次编辑不会新增行（UNIQUE 命中，revision+1），但**一旦未来做了清理再写，又会新建一份备份**——所以"长期只增不减"成立，只是增长单位是"文件 × 清理周期"。
- 结果 B（跨模块门禁）：`cleanupItemGate` 要求同交付**所有** item 都 `synced`（`DeliveryDBPhase.swift:197-211`）。culling 的 confirm 会把同一交付上所有 `written` item 一起翻 `synced`（`DeliveryRepo+Confirm.swift:119` 的 `itemsSynced` 不按 module 过滤），所以"culling 确认过"的文件能过门禁；但"只做过 metadata 编辑、从没确认过"的文件，culling cleanup 会以 `XMP_CLEANUP_INCOMPLETE_ITEMS: module=metadata status=written` 跳过，用户只看到"清理了 0 条"。
- 备份本身没有回收路径：`DeliveryTemporaryFiles` 明确"不碰 .gather-backup-*"（文件头注释），备份的归属只能按 `deliveries.backup_path` 对账；metadata 行不删，对账就永远有主。

**本波目标态**：每个模块都能"确认 → 结束"；结束只删自己的 item，最后一个模块结束时删行+备份；另有保留期 GC 兜底（用户从不点结束也不会无限增长）。

### 1.2 内嵌写回的读/哈希账（逐次）

以 metadata/template 模块、JPEG 内嵌目标为例（按调用顺序）：

| 次 | 位置 | 读什么 | 整文件? | 哈希 |
|---|---|---|---|---|
| 1 | `WritebackService+Execute.swift:371` | 写前基线指纹 | 是 | SHA-256 全文件 |
| 2 | `MetadataWriteRouter.swift:144`（backup） | 整文件 → 解析段 → 写头部备份 | 是 | — |
| 3 | `WritebackService+Execute.swift:407` → `readEmbedded` | ImageIO 解析属性 | 是（ImageIO） | — |
| 4 | `JPEGMetadataWriter.swift:127` | `Data(contentsOf:)` | 是 | — |
| 5 | `JPEGMetadataWriter.swift:148` | 写后校验读回 | 是 | SHA-256 扫描段 |
| 6 | `JPEGMetadataWriter.swift:152` | ImageIO 再解析 | 是（ImageIO） | — |
| 7 | `WritebackService+Execute.swift:203` | 写后基线指纹 | 是 | SHA-256 全文件 |
| 8 | `WritebackService+Execute.swift:209` | 写后回读属性 | 是（ImageIO） | — |

- culling 等模块没有第 1/7 步（无写前基线），是 6 读 2 哈希（扫描段写前/写后各一次）；metadata/template 是 8 读 4 哈希（另加两次整文件指纹）。用户说的"6 次整读 + 6 遍 SHA256"量级正确，方向上还偏乐观。
- 峰值内存：`JPEGDocument.init` 先 `[UInt8](data)`（`JPEGSegments.swift:97`，整文件拷贝一份），再 `scan = Data(bytes[index...])`（:114，再拷一份扫描段），`rebuilding` 又 `output.append(scan)`（:260，再拼一份）。加上调用方持有的 `original` 与 `rewritten`，单张峰值 ≈ 4–6 × 文件；4 路并发写 12MB 文件就是 200–300MB 的纯拷贝。
- 2k × 12MB 的读放大：6 × 12MB × 2000 ≈ **144GB**（metadata/template 是 192GB），写放大另算 24GB。

## 2. 共同地基（W0）

### 2.1 schema：继续 v1，直接扩展 DDL

**决策**：**不 bump 版本、不写迁移**。当前仍在开发期，库是"当前 DDL 唯一真相"：新表直接进 DDL，旧开发库按现有 `ResetPolicy` 归档重建（`.renameOlderOnly`），`user_version` 保持 1。理由：

- 还没有发布用户，迁移链是净负债；上一次 v5→v1 的收敛就是为了摆脱它。
- v1 基线刚收敛，直接改 DDL 最省事，也不会留下"迁移器与建库 DDL 漂移"的第二真相。
- 代价明确：任何拿到旧开发库的人升级后会被归档重建（数据不保），这在开发期可接受，但 reset 日志/诊断必须写明是 schema 形状变化导致。

**DDL 组织**（保持"唯一真相源"）：

```swift
// SchemaCurrent.swift
static let ddl = ddlCore + ddlDomain + ddlIndexes + addendumDDL + workbenchDDL
static let createSQL = ddl + "\nPRAGMA user_version = 1;\n"
```

- 新表集中放 `Schema/SchemaCurrent+DDLWorkbench.swift`（11 张表 + 索引），作为独立片段追加；不改动既有表组文本（索引 SQL 参与指纹，改一个字都会让指纹漂移）。
- `user_version` 不变，`OpenState`/迁移器/版本桥全部不动；旧库靠形状校验判不兼容，走既有归档重建。

**新增表（11 张）**：

| 表 | 用途 | 关键约束 |

## 3. 分项设计

### 3.1 元数据交付生命周期（cleanup / finalize / GC）

#### 3.1.1 目标

1. metadata/template 写回有"确认 → 结束"入口，行为与 culling 对齐；
2. 结束只清自己的 item，共享文件留给最后一个模块收尾；
3. 用户从不点结束也不会无限增长：保留期 GC 自动回收**已确认**的行与备份；
4. 任何删除都可重试、可审计、绝不误删未确认的备份。

#### 3.1.2 协议

```swift
// MetadataAPI 追加 3 个方法（其余不变）
func syncState(_ sessionId: String) async throws -> MetadataDeliveryState
func confirmSync(_ input: Confirmed<SessionReference>) async throws -> MetadataDeliveryState
func finalizeSync(_ input: Confirmed<SessionReference>) async throws -> MetadataDeliveryState

public struct MetadataDeliveryState: Codable, Equatable, Sendable {
    public var pending: Int          // 未写盘
    public var written: Int          // 已写盘未确认
    public var synced: Int           // 已确认未结束
    public var failed: Int
    public var conflict: Int
    public var backupCount: Int
    public var backupBytes: Int64
    public var requiresReloadAck: Bool
    public var rows: [MetadataDeliveryRow]   // pathToken/status/modules/updatedAt
}
```

- `confirmSync` → `DeliveryCoordinator.confirm(sessionId:module:)`，**两次**：`.metadata` 与 `.template`（两个模块分别确认；同一交付的 items 会被一次 `itemsSynced` 全翻，第二次是幂等）。
- `finalizeSync` → `DeliveryCoordinator.finalize(sessionId:module:)`，同样两模块；门禁沿用 `requireReloadAck`。**注意现状**：`DeliveryCoordinator` 的 `requireReloadAck` 默认 `true`，组合根（`Core.swift:124`）没有覆盖——也就是说"未装 C1 时门禁自动关闭"并不成立，无 C1 的会话连 confirm 都会被 `XMP_CONFIRM_REQUIRES_SYNC` 挡住。W1 必须把它改成"检测到 C1 配置/运行才启用"（`c1_required` 设置 + preflight 结果），否则本节的自动确认与 GC 对非 C1 用户全部不可达。
- **默认自动确认，C1 例外**：写入成功后自动对本模块 `confirm`（scope `.module`），否则行永远停在 `written`，既不能 cleanup 也不能 finalize（两者都只收 `synced`），增长无法收敛。例外：当 `requireReloadAck` 打开且本会话尚未 `reload_acked_at` 时，保持 `written`，同步条显示"待 C1 重载"，reload 成功后再自动确认。设置 `metadata_sync_auto_confirm=0` 可回到全手动。
- 自动确认不改变"数据正确性"：写盘成功本来就是用户动作；reload-ack 只影响 C1 显示一致性，不阻止我们把状态推进到可清理。

#### 3.1.3 共享交付的收尾规则

- metadata 的"清理/结束"只做 **drop**（保留 XMP、删行/备份），**不调用现有 `cleanup`**：`cleanup` 在没有外来 item 时会 restore 备份，而备份是"首次写入前的头部"，restore 会把用户后续的元数据编辑一起回滚（还会与其它模块已确认的写回打架）。
- 给 `DeliveryCleanupFlow` 增加 **module 作用域的 finalize**：先删本模块 synced item；若仍有其它模块 item（任意状态）→ 保留交付行/备份并记 `retained` 计数；若已无 item → 走现有 finalize 前滚（prepare → 删备份 → CAS 删行 → finish）。
- 门禁：本模块存在非 synced item → skip 并报 `METADATA_FINALIZE_INCOMPLETE`（提示"先确认再结束"）；外来模块的非 synced item 不阻止"删自己的 item"，但会阻止删行/备份。
- 最后一个模块结束时删行+备份；此前的模块只删自己的 item。这样"谁最后结束谁清理"，不会出现无主备份。

#### 3.1.4 保留期 GC（`MetadataRetentionService`）

批处理，启动后 30s 跑一次 + 每 24h 一次 + 设置页手动触发：

```sql
-- 候选：已确认、超过保留期、无未完成 intent
SELECT d.id, d.xmp_path, d.backup_path, d.updated_at
FROM deliveries d
WHERE d.status = 'synced'
  AND d.updated_at < :cutoff
  AND NOT EXISTS (SELECT 1 FROM delivery_intents i
                  WHERE i.xmp_path = d.xmp_path AND i.phase <> 'applied')
ORDER BY d.updated_at ASC
LIMIT 200;
```

每条走 **finalize 的同一条 intent 前滚**（prepare → 删备份 → CAS 删行 → finish），不另写删除逻辑；失败保留 intent，下次重试。备份删除在 DB 提交之后（与 `DeliveryCleanupFlow+Finalize` 的顺序契约一致）。

GC 的额外门禁：若本机检测到 Capture One 且该会话的 `reload_acked_at` 为空，跳过（C1 仍显示旧值、备份是唯一还原点）；用户可在设置页"立即清理"里显式忽略该门禁。

补充规则：

- **未确认不回收**（`written`/`pending`/`conflict` 一律跳过）——备份是用户唯一撤销点。
- **文件已消失**（`xmp_path` 不存在且无 pending intent）→ 直接删行；备份路径若存在则一并删（它已无处可 restore）。
- **零 item 的孤儿行**（photo 被删导致 CASCADE 清空 items）→ 删行 + 备份。
- **孤儿备份**：只扫"本机会话根目录的第一层"（不递归），文件名匹配 `<basename>.gather-header-*` / `.gather-backup-*` 且 `mtime > 24h` 且 DB 无 `backup_path` 指向它 → 删。用 `DeliveryBackupPath.isControlledName` 做白名单，绝不按前缀盲删。
- **上限**：单次最多处理 200 条，避免长事务；进度进 ControlCenter 后台 job。
- **存量收编（一次性）**：新 DDL 首次启动（库被重建后通常为空，但兼容旧开发库时可能仍有存量）时，把"仅有 metadata/template item、状态 written、无 pending intent、照片仍在"的交付按新策略自动确认（写入成功过一次，缺的只是确认动作），随后交给 GC；数量与结果记日志 + 维护页可见。仍有 failed/conflict 的行不碰。

#### 3.1.5 UI

- 元数据编辑器/挑片同步条新增"同步与备份"状态条：`待写回 N · 待确认 M · 可结束 K · 备份 X MB`；按钮：确认同步（只在"C1 待重载"时出现；reload 成功后自动消失）、结束同步（确认 sheet：删除 N 份备份，XMP 保留）。
- 设置 → 维护：备份统计 + "立即清理" + "结束全部历史元数据同步"（dry-run 先显示条数/字节）。
- 失败可见：结束失败的逐条进 notice（不是静默 0 条），错误码 `METADATA_FINALIZE_*`。

#### 3.1.6 测试

- 写 100 张 → 100 行/100 备份；auto-confirm → 全 synced；finalize → 0 行/0 备份，XMP 指纹不变。
- 自动确认三态：无 C1 → 写完即 synced；C1 待重载 → 保持 written、reload 后自动 synced；`metadata_sync_auto_confirm=0` → 保持 written，手动确认。
- 共享文件：culling 先 confirm+cleanup → 只删 culling item；metadata 后 finalize → 行+备份消失。
- metadata 从未 confirm 时 culling cleanup 被 skip，错误里明确 `module=metadata status=written`（现状已有；新增 UI 提示"先去确认元数据"）。
- GC：保留期 0 天 + 已确认 → 回收；`written` 行不动；备份删除失败 → 行保留、错误可见、下次重试。
- 崩溃点：删备份成功/DB 失败；DB 成功/删备份失败（startup replay 补删）。
- 零 item 行、文件消失、孤儿备份、符号链接（不删）各一条。

### 3.2 内嵌写回：一次读、一次写

#### 3.2.1 目标与预算

| 指标 | 现状 | 目标 |
|---|---|---|
| 整文件读 | 6–8 次 | **2 次顺序遍历**（快照 + 流式拷贝；可选合并为 1 次） |
| 整文件哈希 | 3–4 次 | **2 次**（写前全文件 1 次；写后对"已写字节"增量 1 次，不重读） |
| 峰值内存 | 4–6 × 文件 | 头（≤4MB）+ 1MiB 块 + 重建头 |
| 2k×12MB 读放大 | 144–192GB | ~24GB（+24GB 写） |
| 单张 12MB 写 | ~6 次 decode/read | 0 次 ImageIO 解码 |

#### 3.2.2 会话端口

```swift
public protocol MetadataRewriteSession: AnyObject, Sendable {
    var fingerprintBefore: String { get }          // "size:mtime:sha256"
    var attributes: MetadataWriteAttributes { get } // XMP+IIM 合并（sidecar 覆盖规则不变）
    var headerBytes: Int { get }
    func writeHeaderBackup() async throws -> String
    func commit(_ attributes: MetadataWriteAttributes) async throws -> MetadataRewriteReport
    func abort() async
}

public struct MetadataRewriteReport: Sendable, Equatable {
    public let bytesBefore: Int64
    public let bytesAfter: Int64
    public let fingerprintAfter: String
    public let scanDigest: String
    public let touchedIIM: Bool
    public let headerBackupPath: String
}

public protocol MetadataRewriteSessionFactory: Sendable {
    func open(photoPath: String) async throws -> (any MetadataRewriteSession)?
}
```

- 返回 `nil` = "不是内嵌目标/不支持"（sidecar、RAW、测试替身），`WritebackService` 回退旧路径。这样 `PortFakeSupport` 与 100+ 现有测试不需要改。
- 工厂注入 `WritebackService.init`（默认 nil），生产在 `Core.swift` 组装；`embedded_fast_path=0` 时不注入。

#### 3.2.3 一次读：快照

`EmbeddedJPEGSession.open`：

1. `FileHandle` 打开（`O_RDONLY`），`fstat` 取 size/mtime；
2. 顺序读 1MiB 块，增量解析 SOI→SOS 之间的段（段载荷单独持有，头总量上限 4MiB，超过按 `EMBEDDED_HEADER_TOO_LARGE` 拒绝）；
3. 记 `scanOffset`；从该偏移继续读同一句柄到 EOF，**同时**更新两个 hasher：全文件 SHA-256、扫描段 SHA-256；
4. 用 XMP 包 + APP13 解析出 `attributes`（详见 3.2.5），不调用 ImageIO；
5. 关闭句柄（或保留到 commit；保留可省一次 open，但会占 fd，选"读完即关，commit 复用路径重新 open 并校验 stat 未变"）。

得到：`segments`（仅头部）、`scanOffset`、`fileSize`、`size:mtime:sha256`、`scanDigest`、`attributes`。

#### 3.2.4 一次写：流式重建

`commit`：

1. 用新属性重建头部字节（复用 `JPEGDocument.rebuilding` 的段编辑逻辑，但输出到 `Data`，不拼扫描段）；
2. 在**同目录**建临时文件（`.IMG.JPG.gather-embedded-<uuid>`），写头部；
3. 从原文件 `scanOffset` 起按 1MiB 块读、写临时文件，**每块同时更新两个 hasher：输出文件 SHA-256、扫描段 SHA-256**；写完 `fsync`；
4. **替换前完成全部校验**（失败只删临时文件，原片一个字节都没动，不需要回滚路径）：
   - 临时文件的扫描段摘要 == 快照 `scanDigest`（不等 = 拷贝期间源文件被改 → `XMP_EXTERNAL_EDIT_CONFLICT`）；
   - 对临时文件的头部跑 `XMPPacketReader` + `IPTCIIM.parse`，用 `SidecarXMPProvider.verify` 同款逐字段比较（rating/label/keywords/descriptive/triageSignal）；
   - 临时文件 size == header + scan；
5. `fstat` 原文件，size/mtime 仍与快照一致（否则冲突，删临时文件）；
6. `FileManager.replaceItemAt`（保留权限/ACL/xattr，与现状一致）；失败删临时文件；
7. `fingerprintAfter = "<新 size>:<新 mtime>:<输出 SHA>"`——输出 SHA 在第 3 步已增量算出，**不再读一遍**；`scanDigest` 直接取第 3 步的扫描段哈希。

总 IO：读 1 遍（快照）+ 读 1 遍（拷贝扫描段）+ 写 1 遍 = 2 读 1 写。若把快照与拷贝合并（保留句柄，边读边写临时文件），可降到 **1 读 1 写**，但要求"先决定写什么头"——属性合并需要先读头，所以两段式更稳。**先做 2 读 1 写，留 1 读 1 写为可选优化**（用 `pread` 双游标，读完头即回退，风险更高）。

> 注：用户口径"一次读"在工程上应理解为"一次顺序遍历"；两段式是 O(1) 内存、两次顺序遍历，仍比现状少 4–6 遍整文件读。

#### 3.2.5 读属性不靠 ImageIO：`XMPPacketReader`

现状读属性靠 `ImageIOExifProvider.parse`（`ImageMetadataProviders.swift:24-100`），它会把整份 JPEG 交给 ImageIO 解码。新路径用 Foundation `XMLParser` 解析 XMP 包（≤4MB）：

- 顶层 `rdf:Description` 属性 + 子元素 → `xmp["Rating"]`、`xmp["Label"]`、`dc:subject`、`dc:title`…；
- `rdf:Bag/Seq/Alt` → 数组/多语言；
- `lr:hierarchicalSubject` → 层级关键词（W3 使用）；
- `gather:Triage` → 私有信号；
- 与 `IPTCIIM.parse` 的结果按现有 `embeddedDescriptiveFields` 表合并（键表不改）。

回退：包缺失/解析失败 → 返回 `nil`，由调用方回退 ImageIO 旧路径（只在异常文件上多读一次），并记 `embedded_xmp_parse_fallback` 计数。IFD0 的 `Rating` 兜底（`MetadataService.swift:407`）在新路径中丢失——这是有意的：XMP 是写回权威，IFD0 只在"XMP 无 Rating"时被读，写回本来就会以 XMP 为准；在文档与测试里注明。

#### 3.2.8 测试与基准

- **读次数断言**：用计数 `FileHandle` 包装（`CountingFileHandle`）断言 `bytesRead <= fileSize + 4MiB`，且 `open` 只发生 2 次（快照/提交各一次）。
- **字节保真**：写前后扫描段 SHA 相等；头部段顺序/载荷除被编辑段外逐字节相等（现有 `JPEGSegmentsTests` 的"解析→重建相等"性质测试扩展到大文件）。
- **属性往返**：rating/label/keywords/descriptive 三态 + 清空 + triageSignal；XMP 命名空间别名/多 `rdf:Description` 沿用现有 patch 测试。
- **崩溃安全**：写临时文件后/替换前任一校验失败或注入失败 → 原文件不变、临时文件被删；替换失败 → 原文件不变。没有"替换后回滚"路径（校验全部前移）。
- **并发**：同路径串行（`XMPFileLock` 已有）；不同路径 4 路并发，断言峰值 RSS 增量 < 64MB（用 `task_info` 采样，允许 CI skip）。
- **基准**：`GatherAppTests` 里 200 × 12MB 合成 JPEG，记录总读字节/耗时（不设硬门禁，进 `docs` 报告）；目标 ≤ 60s（M1，APFS）。

#### 3.2.9 风险

- 段编辑的边界（多 APP13、XMP 段在 Exif 前、尾部垃圾字节）——沿用现有测试 + 用真实相机文件语料回归；`JPEGSegmentScanner` 与 `JPEGDocument` 跑同一组性质测试（双实现互证）。
- `replaceItemAt` 在只读介质/网络卷失败——保持现状错误码 `EMBEDDED_ATOMIC_WRITE_FAILED`。
- 大文件（>2GB）Int32 溢出——全部用 `Int64` 偏移与 `Data(contentsOf:options:.mappedIfSafe)` 仅用于测试。
- ImageIO 回退路径保留，作为灰度开关与异常文件兜底。

### 3.5 分享策略：有效期 / 密码 / 下载权限

#### 3.5.1 先说实话

WebDAV 没有"链接"：`baseURL + 账号` 是服务器级凭据，过期与独立密码只能由服务器策略执行。**应用内能强制的只有"上传什么/不上传什么"和"到期后主动撤销"**。设计把这三件事分开命名，UI 不承诺做不到的事。

| 诉求 | 可强制? | 方案 |
|---|---|---|
| 不允许下载原图 | **可** | 发布清单只含 `thumbs/` + `proof.html`；`large/` 只在"允许查看大图"时上传，不传成片目录。proof 页不提供下载链接 |
| 到期后不可访问 | **半强制** | 到期时间写 `share.json` + proof 页显示倒计时并在过期后禁止提交；同时注册"撤销 job"在到期时 DELETE 远端目录（App 需在运行；UI 明示） |
| 独立密码 | 否（WebDAV 账号级） | 两个选项：(a) 使用服务器上单独的分享账号（文档指引）；(b) 加密 DMG 打包后上传（AES-256，macOS 可解，Windows 需 7-Zip） |
| 真正的一次性链接 | 否 | 预留 `ShareGateway` 端口（S3 预签名/对象存储/自建服务），本波不实现 |

#### 3.5.2 类型与流程

```swift
public struct OutputShareOptions: Codable, Equatable, Sendable {
    public var allowDownload: Bool          // false = 只传 thumbs
    public var expiresAt: Date?             // 提示 + 撤销 job
    public var encryptBundle: Bool          // 加密 DMG（密码存 Keychain）
    public var remoteSubfolder: String      // 本次发布的独立目录
}

public protocol ShareGateway: Sendable {
    func publish(bundle: ShareBundle, policy: OutputShareOptions) async throws -> ShareReceipt
    func revoke(_ receipt: ShareReceipt) async throws
}
```

- 发布清单改为**显式 allowlist**（把现有可选前缀升级为必须，修掉 decisions 里记的"WebDAV 上传整 run 根"）：固定上传 `manifest.json / contact-sheet-*.pdf / gallery/index.html / gallery/*.css|js|data.json / gallery/thumbs/** / proof.html|proof.js`；`allowDownload=true` 时再加 `gallery/large/**`。**成片目录永不默认上传**，需要时单独勾选。
- `allowDownload=false` 时画廊的 `data-large` 指向 `thumbs/`（lightbox 用缩略图，质量降级但不泄露大图）；这是有意的取舍，UI 要写明"关闭下载会降低灯箱清晰度"。
- `share.json`：`{createdAt, expiresAt, allowDownload, itemCount, contact}`，随包上传；proof 页读取并在过期后禁用提交。
- 撤销：`ShareRevokeJob`（JobService 持久化）到期执行 `DELETE` 远端 `remoteSubfolder`；失败重试 3 次并进诊断。App 未运行时无法撤销——UI 文案明示。
- 加密包：`hdiutil create -srcfolder <bundle> -encryption AES-256 -stdinpass`，密码进 Keychain，上传单个 `.dmg`；不提供密码找回。

#### 3.5.3 测试

- allowlist：`allowDownload=false` 时 `large/` 与成片目录 0 请求（假 transport 断言请求路径集合）；
- 过期：proof 页 JS 单测（注入时钟）；撤销 job 幂等（404 视为成功）；
- 加密：命令拼装单测（不真的加密大文件）；密码不落日志（日志脱敏断言）。

### 3.6 关键词体系 + keyword facet

#### 3.6.1 数据模型

```sql
CREATE TABLE keywords (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  path TEXT NOT NULL UNIQUE,        -- "A|B|C"，NFC、trim、段非空
  name TEXT NOT NULL,               -- 叶子
  parent_path TEXT,                 -- "A|B" 或 NULL（改名时事务内级联）
  usage_count INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);
CREATE TABLE keyword_synonyms (
  keyword_path TEXT NOT NULL REFERENCES keywords(path) ON DELETE CASCADE,
  synonym TEXT NOT NULL,            -- fold 后去重
  PRIMARY KEY (keyword_path, synonym)
);
CREATE TABLE photo_keywords (
  photo_id TEXT NOT NULL REFERENCES photos(id) ON DELETE CASCADE,
  keyword_path TEXT NOT NULL,
  source TEXT NOT NULL DEFAULT 'xmp'
    CHECK (source IN ('xmp','culling','face-keyword','similarity','manual')),
  PRIMARY KEY (photo_id, keyword_path)
);
CREATE INDEX idx_photo_keywords_path ON photo_keywords(keyword_path, photo_id);
```

- 为什么 `photo_keywords` 用 `photo_id` 而不是 `xmp_path`：facet 与网格必须同口径（网格按 photo 行分页），跨会话同文件各自一行是可接受的重复；写入仍按 xmp_path 分组（`MetadataMutationService` 不变）。因此 **facet 计数必须按 `COALESCE(asset_id, photo_id)` 去重**（与网格同口径），`keywords.usage_count` 只作排序权重，不能当展示计数。
- `keywords` 不设 `parent_id`：路径即层级，改名 = 事务内 `UPDATE path/parent_path` + `photo_keywords` 前缀更新，避免递归 CTE。

#### 3.6.2 编解码

`KeywordPath`（纯值）：

```swift
public struct KeywordPath: Hashable, Codable, Sendable, Comparable {
    public let segments: [String]     // ["A","B","C"]
    public var serialized: String     // "A|B|C"
    public var leaf: String
    public var ancestors: [String]
}
```

- 读：`dc:subject`（可能含 `A|B` 也可能只有叶子）+ `lr:hierarchicalSubject`（路径）→ 合并去重（fold）。同路径以层级为准，叶子重复不重复计数。
- 写（`keyword_dc_style`）：
  - `leaf`（默认）：`dc:subject` = 所有叶子（含层级叶子，去重）；`lr:hierarchicalSubject` = 所有含 `|` 的路径。
  - `path`：`dc:subject` = 所有完整路径 + 平铺词；`lr:hierarchicalSubject` 同。
- 兼容性：Lightroom/Bridge 读 `lr:hierarchicalSubject` 建层级；C1 的导入行为需实机确认（按其关键词库规则）。平铺词不写 `lr:`（写了会被当成一级路径，造成重复）。

#### 3.6.3 写回链路

- `MetadataWriteAttributes.keywords` 仍是 `[String]`（wire 不变，delivery_items.keywords 不用迁移），在边界用 `KeywordPath.serialized` 编码；`MetadataService` 的 `normalizeKeywordList` 改为走 `KeywordPath.parse`（非法段丢弃而非整词丢弃）。
- `SidecarXMPProvider+Patching.swift` 增加 `lr:hierarchicalSubject` 的 insert-or-replace（与 `dc:subject` 同构，`rdf:Bag`），命名空间 `http://ns.adobe.com/lightroom/1.0/`；`verify` 增加两套列表的逐项比较（含清空）。
- 内嵌：`XMPPacketReader` 解析 `lr:` 命名空间（ImageIO 不回传未知命名空间，必须自己解析）；写侧 `XMPPacketStore.patched` 同样补 `lr:`。
- IIM：`IPTCIIMMapping` 继续只写叶子（IIM 无层级），避免把 `A|B` 写进 2:25 被其它软件当单字关键词。

#### 3.6.4 同步与 facet

- 索引/扫描完成、写回成功、校样导入后：`KeywordIndexSync` 对一个 photo 做 diff（`photo_keywords` 增删 + `usage_count` 重算），单事务。
- 回填：新库首次索引/首次启动时把 `photo_metadata_cache.keywords` 全量导入（每 5k 行一批，后台 job，可断点；以 `photo_keywords` 是否存在判断幂等）。
- `FacetDimension.keyword`：

```sql
-- 顶级 facet（未指定前缀）
SELECT CASE WHEN instr(pk.keyword_path,'|')>0
            THEN substr(pk.keyword_path,1,instr(pk.keyword_path,'|')-1)
            ELSE pk.keyword_path END AS v,
       COUNT(DISTINCT COALESCE(NULLIF(p.asset_id,''), p.id))  -- 按逻辑资产，避免跨会话重复计数

...
```

- 同维剔除：facet 维度字段名 `keyword_path`，`FilterGroup.removing(field:"keyword_path")`；点击 facet 生成 `startsWith` 规则（下钻）或 `in`（叶子多选）。

#### 3.6.5 词库与同义词

- 4 档里的 `hasFace/noFace` 可映射到 `face_count`；`offline` 目前在 `FilterEngine` 没有公开字段，**不要**把它塞进用户可编辑字段白名单——给 `FilterGroup` 加一个 internal 谓词（只由 Gallery 的开关生成），或保留为独立查询参数。实现时先用 `EXPLAIN` 确认不引入全表扫描。
- 生效条件：criteria 非空 → 走新分页（清空游标链，选择集清空）；清空 → 回到原游标链并从第一页重载（现有 `commitSearch` 已有"退出搜索保留首页"的逻辑，扩展它）。
- 保存查询：搜索框右侧菜单"保存当前筛选…"；列表含全局/本会话；点击应用（criteria + 搜索词 + 4 档整体恢复）。

#### 3.7.3 协议与数据

- `saved_searches`：`id/name/session_id/criteria_json/created_at/updated_at`；上限 `gallery_saved_search_limit`（默认 50），超限报 `SAVED_SEARCH_LIMIT`。
- 推荐新增独立 `SearchAPI`（4 个方法：`savedSearches(sessionId:)`、`saveSearch(input)`、`deleteSavedSearch(id)`、`count(criteria:sessionId:)`），不往 `PhotoAPI` 里塞（它已有 9 个方法）。代价是协议面 +1 类型 +4 声明，收益是职责清晰、Gallery/Library 共用。
- 计数：facet 用 `PhotoAPI.facets`（已支持 session）。`PhotoPage` 目前只有 `rows` + `cursor`（`PhotoOutputs.swift:14-22`），没有 total；推荐在 `SearchAPI` 加 `count(criteria)`（一次 COUNT，不带分页），**不要**给 `PhotoPage` 加 total（否则每翻一页多一次 COUNT）。

#### 3.7.4 测试

- 分页 + criteria：同一条 SQL 的行序稳定、跨页无重复/漏项（与 `PhotoPage` 现有测试同法）；
- facet 点击 → 网格计数一致；
- 保存/恢复查询（含 4 档 + 搜索串）；
- 20k 会话：criteria 命中 500 时首屏 < 300ms（EXPLAIN 断言走索引，不出现全表 + 临时 B-TREE）；
- 退出筛选恢复游标链，无重复行。

### 3.8 策展容器：集合 / 堆栈 / 跨工作区

#### 3.8.1 手动集合

```sql
CREATE TABLE collections (
  id TEXT PRIMARY KEY,
  session_id TEXT REFERENCES sessions(id) ON DELETE CASCADE,  -- NULL = 跨会话集合（本波不做 UI）
  name TEXT NOT NULL,
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE TABLE collection_items (
  collection_id TEXT NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
  photo_id TEXT NOT NULL REFERENCES photos(id) ON DELETE CASCADE,
  position INTEGER NOT NULL,
  added_at TEXT NOT NULL,
  PRIMARY KEY (collection_id, photo_id)
);
CREATE INDEX idx_collection_items_order ON collection_items(collection_id, position);
CREATE UNIQUE INDEX idx_collections_session_name ON collections(session_id, name);
```

- **顺序**：`position` 用步长 1024 插入（拖拽时取前后中点），冲突/耗尽时事务内重排（1..n）。这样单次拖拽只写 1 行，不重写全表。
- 协议 `CollectionAPI`（新，6 方法）：`collections(sessionId)`、`createCollection`、`renameCollection`、`deleteCollection`、`addItems`（尾部追加/去重）、`reorderItems`（显式 id 顺序）。
- UI：会话侧栏"集合"分组；拖照片进集合（网格多选拖拽 + 检查器"加入集合"菜单）；集合视图复用 Gallery 网格（有序、无排序控件，支持 ⌘↑↓ 微调 + 拖拽）。
- 导出：导出范围增加"当前集合"（`ExportScope.collection(id)` 或直接传 `selectedPhotoIds`，推荐后者，避免扩枚举）。

#### 3.8.2 堆栈

```sql
CREATE TABLE photo_stacks (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  name TEXT NOT NULL DEFAULT '',
  cover_photo_id TEXT REFERENCES photos(id) ON DELETE SET NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE TABLE photo_stack_members (
  stack_id TEXT NOT NULL REFERENCES photo_stacks(id) ON DELETE CASCADE,
  photo_id TEXT NOT NULL REFERENCES photos(id) ON DELETE CASCADE,
  position INTEGER NOT NULL,
  PRIMARY KEY (stack_id, photo_id)
);
```

- 合并展示：网格把同 stack 的成员折成一张（封面 + 右上角 `n` 徽标），点开抽屉/双击展开；与 `expandVariants`（RAW/JPEG 折叠）正交：先按 asset 折叠，再按 stack 折叠。
- 创建：多选 → "堆叠"；或"从连拍组创建"（读 `navigation_groups type=burst`，一键成堆）；解堆、设封面、改名。
- 排序：堆内按 `position`；新照片追加尾部。
- 与选片：堆栈只影响展示，不影响 score/decision；"只显示每组最佳"作为集合式快捷筛选（可后置）。

#### 3.8.3 跨工作区重复/相似（只读）

现状：`duplicate_groups.session_id NOT NULL`、`similarity_hashes.session_id NOT NULL`，但 **hash/checksum 值本身是内容属性**，跨会话可比：

- 精确重复：`GROUP BY checksum HAVING COUNT(DISTINCT session_id) > 1`（`photos.checksum` 已有；懒计算的要先补算，显示"未计算"）。
- 视觉重复：先按 `hash_hex` 精确分组（同图不同会话哈希应一致；若确认哈希掺入了会话/路径盐，则只保留精确 checksum 分组并在 UI 标注"仅精确重复"），桶内再做汉明 ≤14 的两两比较（桶内数量上限 64，超出只做精确分组并提示）。
- 新服务 `GlobalDuplicateService.scan()`：后台 job、可取消、结果缓存在内存（不新增表；如需要持久化再加 `global_duplicate_groups`）。
- UI：Library 侧栏"跨工作区重复"；每组显示缩略图 + 所在工作区 + 文件大小/时间；操作 v1 只读（"在访达显示"/"跳到该工作区"），**不做跨工作区删除**（删除语义涉及两个工作区的可见性，风险高于价值）。
- 性能：20 个会话 × 2k 张，`GROUP BY checksum` 走索引 <100ms；视觉桶比较在 Swift 侧，上限 50k 行。

#### 3.8.4 虚拟副本：本波不做（明确记录）

理由（三条，按重要性）：

1. **双真相源**：Gather 的写回模型是"一个文件一份 XMP"；虚拟副本若只存 DB，就与 C1/Lightroom 的"文件级变体"语义冲突，导出/写回时必然要选边。
2. **C1 不认**：C1 的变体是 `.cos` 里的条目；我们造一个 `IMG_0001~2.xmp`，C1 不会读，Lightroom 也不会——用户看到的是"多出来的孤儿 sidecar"。
3. **收益/成本**：虚拟副本主要服务于"同一张底片多套调色"，而 Gather 没有 develop 管线；本波做出来只能承载评分/关键词差异，用"堆栈 + 集合 + 备注"已能覆盖 80% 的挑片场景。

替代方案（若未来要做）：`photo_variants` 表 + 变体自带 rating/label/keywords + 导出时按变体生成不同 XMP 副本，并在 UI 明确标注"仅 Gather 可见"；届时再单独立项。

### 3.9 挑片可视化

全部基于**已经加载的 1280 预览**（CullingWorkbenchViewer 现有 `preview`），不新增解码；开关默认关，状态存会话内存。

#### 3.9.1 直方图

- `PreviewHistogram`：把预览降采样到 256px 长边，统计 64 bin 亮度 + RGB 三通道，附"高光溢出/阴影死黑"百分比。
- UI：查看器右下角 160×80 Canvas，`H` 切换；RGB 叠加 + 亮度折线；点直方图可切换"仅亮度/三通道"。快捷键统一进 `Interaction/` 的键位表（H/F/P/R/C/O 若与现有键冲突改用 ⌥ 组合，不硬编码在视图里）。
- 语义：**预览直方图**，不是 RAW 线性数据；UI 标注"基于预览"，避免被当成曝光工具。
- 计算在 `Task.detached(priority: .utility)`，结果按 `photoId#previewVersion` 缓存（LRU 8）。

#### 3.9.2 合焦提示（focus mask / peaking）

- `FocusMap`：1280 灰度 → 3×3 局部方差（积分图 O(n)）→ 归一化到 0…1；阈值 `focus_mask_threshold`（默认 0.55）。
- focus mask：把 320px 的二值 mask 叠成红色 35% 透明层（Canvas 绘制，不生成位图文件）。
- peaking：对显示分辨率做 Sobel，边缘幅值 > 阈值的像素描白（1px），用于手动对焦确认。
- 性能：1280 上积分图 ~2ms、320 mask ~1ms；切换 <16ms，无卡顿。
- 文案：叫"合焦提示"，不叫"焦点掩膜"——这是启发式，不是相机 AF 数据。

#### 3.9.3 AF 点

- `AFPointExtractor`：优先 ImageIO `kCGImagePropertyExifAuxDictionary` 的 AF 相关键（Canon/Nikon 部分机型可见）；不可见时对 MakerNote 做有限扫描（只认已登记机型偏移表，不做通用解析）；仍无 → 回退"主体人脸框中心"。
- UI：图上画 AF 框（白色 1px + 角标）；点击 AF 框 → 以该点为中心 100% 缩放；无数据时菜单项禁用并提示"该机型无 AF 数据"。
- 取舍：不做全机型 MakerNote 逆向；登记表放 `AFPointProfiles.swift`，可增量加。

#### 3.9.4 旋转/裁剪标记

- 读 `tiff:Orientation`（ImageIO 已应用）与 XMP `crs:Angle / crs:CropTop/Left/Bottom/Right`（Lightroom 约定，C1 开启"包含调整"时也写）。
- 绘制：虚线裁剪框 + 角度徽标 + "已裁剪"角标；`O` 切换"显示全图"（临时去掉裁剪蒙版）。
- **只读**：Gather 不提供裁剪编辑；这里解决"预览与 C1 看到的不一样"的困惑，不承诺编辑。

#### 3.9.5 参考对比（reference compare）

- 参考槽：`R` 把当前照片设为参考（同会话内保持，切页不丢）；再按 `R` 取消。
- 三种模式（`C` 循环）：并排（现有 compare2 复用）、分割线（可拖动，左右各半）、50% 叠加。
- 同步：缩放/平移共享一个 `TransformState`（参考与当前同缩放系数、同归一化中心）；`\` 交换主/参考。
- 指示：查看器左上角"参考：IMG_0001"徽标；参考照片不在当前页时仍可加载（按需取预览）。
- 与现有 compare2/4 的关系：compare2/4 是"多张平铺"，reference 是"一张基准 + 一张当前"，共存，不合并。

#### 3.9.6 before/after：不做（明确记录）

Gather 没有 develop 管线，"before/after"没有可比的渲染版本；用"参考对比"覆盖真实需求（挑片时和基准帧比较）。若未来接 C1 渲染预览（3.10.3），可把"before"定义为"C1 渲染 vs 内嵌预览"，届时再立项。

#### 3.9.7 测试

- `PreviewHistogram`：全黑/全白/棋盘/渐变 → bin 分布金样；clipping 百分比；
- `FocusMap`：纯色图 → 全 0；棋盘 → 高频区域高值；阈值边界；
- `AFPointExtractor`：3 个真实机型样本（fixture EXIF）+ 无数据；
- 裁剪框几何：角度 0/90/负角度、裁剪越界夹取；
- 参考对比：分割线位置 ↔ 图像坐标映射、缩放同步（纯函数）。

### 3.10 Capture One 往返

#### 3.10.1 自动 reload

- `C1RoundTripCoordinator`（Host，@MainActor）：
  - 订阅 `deliveryStateChanged`（现有事件），按 session 聚合；
  - 写回批次结束（`written`/`failed` 收敛）后 debounce 1.5s；
  - 条件：`c1_auto_reload=1`、preflight 可达且文档打开、本批至少 1 条成功；
  - 调 `bridge.reloadMetadata(sessionId:)`（内部已有 500ms 窗口 + durable ack）；
  - 失败：非阻塞 notice（"C1 未重载：<原因>，请在 C1 手动 Load Metadata"），并保留"重试"按钮；不阻塞交付结果。
- 不在 `execute` 事务内调用；不并发多个 reload（串行队列 + 合并）。

#### 3.10.2 在 C1 中打开选中

- `CaptureOneBridge.selectVariants(paths:)`：
  - 首选 AppleScript：按路径逐个 `whose path is "<posix>"` 匹配后 `select`（AppleScript 没有 `in {…}` 集合字面量，必须循环/单值比较；路径要转义）；按 C1 版本探测语法，失败走 fallback；
  - fallback：`NSWorkspace.open([url])`（C1 可能走导入，需在 UI 明示"可能触发导入"）；
  - 预检不通过时菜单项禁用（拿到 `C1PreflightStatus`）。
- 入口：挑片工具栏"在 C1 中显示"（⌘⇧O）、元数据编辑器、交付结果页"在 C1 中查看"。
- 新错误码：`C1_SELECT_FAILED`、`C1_SELECT_UNSUPPORTED`（脚本不支持时提示升级 C1 / 用访达）。

#### 3.10.3 预览与 C1 调整

- **能做的**：
  - 旋转：`tiff:Orientation` 已由 ImageIO 应用；`crs:Angle` 作为额外旋转叠加（可选开关）；
  - 裁剪：读 `crs:Crop*` 画框/蒙版（与 3.9.4 同一实现）；
  - 标注：当 XMP 存在 `crs:` 字段而预览未应用时，显示"预览可能不含 C1 调整"提示（避免用户以为我们静默忽略了）。
- **不能做的**：C1 的色彩/曲线/局部调整在 `.cos`（私有格式），不解析。**不要**用"读 .cos"作为承诺。
- 可选（默认关，feature flag `c1_rendered_preview`）：AppleScript 让 C1 把当前变体导出为临时 JPEG（长边 1600），按 `.cos` mtime 缓存；单张 0.5–2s，只对"正在查看的 1 张"做，不做批量。这条作为后续增强，不阻塞本波。

#### 3.10.4 测试

- 自动 reload：假 bridge 计数（批次结束只 reload 一次、debounce 合并、失败不重试风暴）；
- 选择脚本：脚本文本金样 + 路径转义（引号/反斜杠/Unicode）；
- 预检失败 → 菜单禁用；
- 裁剪/角度叠加几何。

### 3.11 AI 流程深度

#### 3.11.1 导入后自动初审

- 触发点：`IngestService` 的 job 收尾（`JobService.settle`）后，若 `triage_auto_generate=1`，为本次新增 photoIds 入队 `analysis.pipeline`：
  1. quality.analyze（缺失才跑）；
  2. model.review（`triage_model_review=1` 且策略 v2）；
  3. triage.generate；
  4. 可选 apply（`triage_auto_apply=1`，仍受 `TriagePolicy.executionFloor` 门禁）。
- 用现有 JobService（持久化/恢复/取消）串成一条 job，阶段进度进 ControlCenter；同一 session 去重（`input_fingerprint` 已存在）。
- 只处理新照片：把 `photoIds` 写进 job payload；已分析的跳过（质量行存在且指纹一致）。
- 取消：任何阶段取消 → job `cancelled`，已产出的建议保留但标记 `partial`（不写 apply）。
- 不做：导入时同步阻塞分析（会拖慢导入）；不做"导入完成弹窗"。

#### 3.11.2 阈值校准

- 数据集（只取人工决定）：

```sql
SELECT t.verdict, t.confidence, t.score, cd.decision, p.session_id, pmc.camera_model, pmc.iso
FROM triage_suggestions t
JOIN culling_decisions cd ON cd.photo_id = t.photo_id
JOIN photos p ON p.id = t.photo_id
LEFT JOIN photo_metadata_cache pmc ON pmc.photo_id = t.photo_id
WHERE cd.source IN ('manual','imported') AND cd.revision > 0
```

- `TriageCalibrationService.report(scope:)`：按 confidence 分 10 桶，算每桶的"建议 keep 且用户也 keep"精确率；给三条候选阈值（保精确率 0.90/0.95/0.98）+ 对应 keep/reject/review 数量。
- UI：设置 → 技术质量建议 → "校准"：曲线图 + 当前阈值 vs 建议阈值 + 样本量；样本 < `triage_calibration_min_samples` 时只显示"样本不足"，禁用"应用"。
- 应用：写三个设置键，并让建议失效重算。**不要**把 `triage_policy` 改成 `triage-v2.<n>`：`TriagePolicy.usesModelSignals` 用 `version == "triage-v2"` 精确比较（`TriagePolicy.swift`），改了会让模型信号静默失效。正确做法：给 `TriagePolicy` 增加 `thresholdFingerprint`（version + 三个阈值的哈希），把它并入 `triage_suggestions.input_fingerprint` 的材料；版本字符串保持不变。
- 不自动应用、不按会话偷偷调参；校准是用户动作。

#### 3.11.3 置信度 UI

- 现状：卡片刻意不显示裸 confidence（`CullingTriageCard.swift` 头注释），避免"0.83 看着像精确概率"。
- 设计：列表/网格显示**三档**（高/中/低，阈值由设置推导）；检查器点"为什么"显示裸值 + 各信号贡献（`TriageReason` 已有）+ 该校准桶的历史精确率（若有）。这样既满足"置信度可见"，又不制造假精度。

#### 3.11.4 学习用户保留/淘汰

- 写入点：`CullingService` 在用户 apply/手动改决策时，与 `triage_suggestions` 当前行对比，写 `triage_feedback(suggestion_verdict, suggestion_confidence, user_action, policy_version, acted_at)`；同一 photo 多次改只留最后一条 + 计数。
- 用途一：校准（3.11.2）的样本来源；用途二：评估（GatherTriageEval 可读表，不再只依赖导出文件）。
- **不做在线训练/模型更新**：没有训练基础设施，也不该用几十条反馈去调 Vision 模型；能做且诚实的是"阈值校准 + 分机型/ISO 的可靠性报告"。

#### 3.11.5 场景/语义分组与语义搜索

- 采集（跟随 model.review 的 1280 解码，边际成本低）：
  - `VNGenerateImageFeaturePrintRequest` → `VNFeaturePrintObservation`（Float32，维度随系统，~2048）；
  - `VNClassifyImageRequest` top-8 标签 + 置信度；
  - 存 `photo_semantics(photo_id, labels_json, feature BLOB, model_version, computed_at)`，Float16 压缩（~4KB/张，20k = 80MB；默认只对开启语义索引的会话建）。
- 场景分组：`NavigationService` 的 scene 组在时间/目录之外加"标签 Jaccard ≥ 0.5 或 embedding 余弦 ≥ 0.92"；仍用 `group_type='scene'`，`explanation` 写明依据（"同场景：婚礼/室内"）。
- 语义搜索：
  - 图搜图：当前照片的 embedding → 会话内/全库 top-N（余弦；20k × 2048 全扫 ~40M 次乘加，~50ms，可接受；超 50k 建 IVF 简版）。
  - 文搜：只做"标签文本匹配"（Vision 标签是英文，UI 显示本地化映射），**不做 CLIP 文本编码**（无模型资产，零依赖约束）。
  - UI：搜索框旁"相似照片"按钮；结果网格复用 Gallery，带相似度徽标。
- 隐私：全部本地；设置里可清空 `photo_semantics`。

#### 3.11.6 测试与基准

- 管线：导入 10 张 → 一条 job、三阶段、进度单调；取消后无 apply；重复导入不重复分析；
- 校准：合成 200 条（已知精确率）→ 报告阈值在期望区间；样本不足禁用；
- 反馈：decision 变更写一条 feedback，重复变更只留最后；
- 语义：两张同图不同尺寸 → 余弦 > 0.95；黑白/翻转 → 距离变大；20k 索引内存峰值 < 200MB；
- 兼容：Vision 请求不可用（旧系统）→ 跳过并记 `semantic_unavailable`，不阻断初审。

### 5.4 设计反思（自我批判）

1. **"一次读"是营销口径，工程上是两遍顺序遍历**。验收必须写 2.1× 而不是 1.1×；否则实现者会被指标逼着做 `pread` 双游标，风险大于收益。
2. **自动确认容易被读成"绕过 C1"**。必须把"C1 待重载 → 保持 written"做成显式状态，并在 UI 上说明"确认的是数据落盘，不是 C1 已刷新"。
3. **DDL 直接扩展会让所有旧开发库被归档重建**：接受（开发期），但要把 reset 原因做成可见日志，避免"数据莫名其妙没了"。
4. **`photo_keywords` 按 photo_id 会在跨会话同文件上重复计数**；facet 必须按逻辑资产 `DISTINCT`（与网格 `asset_id` 口径一致），否则 20k 库里同一个文件在 3 个会话出现会把 facet 数字放大 3 倍。
5. **"下载权限"只能做到"不上传"**，做不到"允许看、不允许存"；这不是权限系统，UI 不能用"权限"二字。
6. **砍掉虚拟副本会让一部分 C1 用户失望**；release notes 要写清楚"堆栈 + 集合 + 备注"能做什么、不能做什么，别让他们以为是 bug。

## 8. 未决问题（附推荐）

1. **schema 扩展的评审口径**：新表直接进 v1 DDL、旧库归档重建（§2.1）。需要确认的是"这批 11 张表一次加完"，而不是每波各改一次 DDL——后者会让开发机反复清库。
2. **`dc:subject` 默认写叶子还是全路径？** 推荐默认 `leaf`（`dc:subject` 里不出现 `|`，最小惊讶），需要完整路径的工作流切 `path`；先各做一份金样，用 C1/Lightroom 实机读回后再定默认。
3. **metadata 的确认入口放哪？** 推荐 `MetadataAPI`（与写回同域，发现性最好）；不推荐新开通用 `SyncAPI`（会与 culling 的 `finalizeSync` 语义分叉）。
4. **校样评论是否写 XMP？** 推荐只存 DB。写 `dc:description` 会覆盖摄影师自己的说明，且 C1 不区分"客户评论"。
5. **"结束同步"是否自动删备份？** 推荐是（finalize 的语义就是丢弃还原点），但要有确认 sheet 与"保留备份"复选框（默认不勾）。
6. **到期撤销 job 的默认行为？** 推荐默认开启，但首次发布时提示"需要 Gather 在到期时运行"；不允许静默失败。
7. **C1 "在 C1 中打开" 的 fallback 是否用 `open`？** 推荐用，但 UI 标注"可能触发导入"；若用户反感，改为只支持 AppleScript 选择。
8. **语义索引默认开还是关？** 推荐默认关，设置里"为当前工作区建立语义索引"；避免首次导入就多 80MB。
9. **虚拟副本是否彻底放弃？** 本波放弃；若后续要做，先写 ADR 明确"Gather-only 变体"的边界，再立项。
10. **跨工作区重复是否允许删除？** 推荐 v1 只读；删除涉及两个工作区的可见性/回收站语义，单独设计。
